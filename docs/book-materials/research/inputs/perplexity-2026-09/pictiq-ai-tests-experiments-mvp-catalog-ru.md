# **Каталог ИИ-тестов, экспериментов и MVP для Pictiq**

## **Уровень 1 — быстрые тесты (часы-дни, без обучения моделей)**

1. **Zero-shot распознавание иконок VLM.** Показать GPT-4V/Gemini/Claude все 52 иконки без подсказок, попросить угадать значение, замерить точность. Потом повторить с переданным лексиконом как контекстом. Разница между двумя прогонами — конкретная цифра "насколько ИИ нуждается в словаре так же, как человек".  
2. **Constrained decoding "из коробки".** Заставить LLM через встроенный structured output/function calling выдавать только валидные ID тайлов по JSON Schema лексикона — без вашего RAG-слоя. Сравнить точность с уже собранным RAG-прототипом: возможно, современные модели вообще не нуждаются в retrieval-шаге для закрытого словаря такого размера.  
3. **Обратный тест — "прочитай последовательность".** Дать модели случайную композицию тайлов без объяснений и попросить восстановить смысл, потом повторить с лексиконом. Показывает, какие композиции реально неоднозначны даже для сильной модели — прямая обратная связь дизайну грамматики.  
4. **Тест согласованности между моделями.** Одна и та же фраза, один и тот же лексикон, 5 разных моделей (GPT/Gemini/Claude/Llama/др.) переводят её в тайлы. Расхождение между ответами показывает, какие концепты кодируются однозначно, а какие — предмет выбора, а не факта.  
5. **Стресс-тест на идиомы и метафоры.** Специально подобрать 10-15 "вредных" фраз (сарказм, идиомы, двойное отрицание) и посмотреть, где ломается и грамматика, и LLM-переводчик поверх неё. Дёшево и быстро выявляет границы применимости.

## **Уровень 2 — небольшие MVP (дни — пара недель)**

6. **Публичное веб\-демо RAG-прототипа.** Уже собранный `pictiq_rag_prototype.py` довести до сайта с кнопкой "это неверно" — реальные пользователи бесплатно генерируют данные об ошибках вместо вас.  
7. **MCP/agent-инструмент "Pictiq translator".** Обернуть текст↔тайлы как вызываемый инструмент для любого LLM-агента — конкретная интеграционная задача, которую можно сделать за один присест.  
8. **CLIP-классификатор без обучения.** Готовые модели вроде CLIP умеют сравнивать фото с текстовыми/эталонными описаниями без дообучения — можно взять фото реального напечатанного тайла (под углом, при плохом свете) и сравнить его эмбеддинг с эмбеддингами 52 канонических SVG. Дешёвый способ проверить, распознаётся ли физический продукт камерой без создания собственной CV-модели с нуля.  
9. **Pictiq → голос.** Взять последовательность тайлов, попросить LLM собрать из неё естественную фразу, озвучить через синтез речи. Замыкает полный AAC-сценарий "человек ткнул иконки → рядом прозвучала фраза" — полезная демонстрация для питча AAC-ниши.  
10. **Предиктор следующего тайла.** В `icon-index.json` уже есть поле `examples` с реальными типовыми композициями — из них можно построить простую модель "какой тайл вероятнее следующий", без сбора новых данных с нуля. Прямой аналог PrAACT/GenAAC подхода, но с бутстрапом на уже существующих данных репозитория.

## **Уровень 3 — исследовательские эксперименты (недели, годятся для публикации/блога)**

11. **Открытый бенчмарк понимания Pictiq моделями.** Формализовать тест №1 в полноценный датасет \+ таблицу результатов по нескольким моделям и опубликовать — конкретный, цитируемый вклад, почти бесплатный при наличии теста №1.  
12. **Эксперимент "ИИ говорит с ИИ только тайлами".** Два независимых LLM-агента решают простую координационную задачу (один знает цель, должен объяснить второму), но им разрешено обмениваться только валидными последовательностями тайлов — без свободного текста. Прямая, наглядная проверка тезиса про интерпретируемый протокол между агентами вместо непрозрачного emergent-языка.  
13. **Замер реальной компрессии промпта.** Взять типовой набор туристических/сервисных интентов, замерить разницу в токенах/стоимости между "полный текст" и "последовательность tile-ID" при отправке в LLM API много раз подряд — превращает пока умозрительный тезис про экономию на IoT-сценариях в конкретную цифру.  
14. **Тест устойчивости к prompt injection.** Сравнить чат-бота со свободным текстовым вводом и бота, ограниченного только тапами по валидным Pictiq-тайлам, прогнав через оба стандартные инъекционные payload'ы. Проверяет эмпирически, а не декларативно, тезис "закрытый словарь \= меньше поверхности атаки".

# **Эксперимент: два ИИ общаются только тайлами Pictiq**

## **Исследовательский вопрос**

Могут ли два независимых ИИ-агента решить задачу координации, обмениваясь исключительно валидными последовательностями Pictiq-тайлов — и как это сравнивается со свободным текстом по успешности, длине сообщений и типам ошибок. Это прямой аналог классических "referential/signaling games" из литературы об эмерджентном языке между агентами (та же парадигма, что у [Havrylov & Titov](https://arxiv.org/abs/1705.11192), которых упоминали раньше), только вместо того, чтобы дать агентам изобретать код с нуля, им дают уже готовый закрытый протокол — и проверяют, справляются ли они с ним лучше, чем со свободной изобретённой системой.

## **Формат — сигнальная игра с судьёй**

Роли:

* **Sender (A)** — получает приватную карточку сценария на естественном языке (её не видит Receiver). Обязан закодировать её в валидную последовательность Pictiq-тайлов, следуя грамматике из `GRAMMAR.md`.  
* **Receiver (B)** — видит только последовательность тайлов, без исходного текста. Должен реконструировать, что имел в виду Sender, и предложить действие.  
* **Судья (я/скрипт)** — знает исходный сценарий, сравнивает реконструкцию B с эталоном по заранее заданным слотам, проверяет, что A использовал только валидные тайлы в допустимом порядке.

Ключевое методологическое решение: карточки сценариев составляются **только из уже существующих 52 иконок**. Если сценарий требует понятия, которого нет в лексиконе, эксперимент перестаёт проверять протокол и начинает проверять полноту словаря — это две разные вещи, их нельзя смешивать.

## **Примеры карточек (только реальный лексикон)**

| \# | Сценарий (видит только A) | Ожидаемая композиция | Слоты для оценки |
| ----- | ----- | ----- | ----- |
| 1 | Нужна вода срочно, денег нет | `need_water + punct_exclaim + money_coins + logic_no` | нужда=вода, срочность=да, деньги=нет |
| 2 | Нужна медпомощь возле отеля | `safety_medical + place_hotel` | нужда=медицина, место=отель |
| 3 | Нужно два туалета, не сейчас | `need_toilet + qty_2 + time + logic_no` | нужда=туалет, количество=2, срочность=нет |
| 4 | Такси до аэропорта, есть карта (оплата) | `move_taxi + place_airport + money_card` | движение=такси, место=аэропорт, оплата=карта |

Каждый слот оценивается 0/1 (совпал/нет) — это даёт не просто "успех/провал", а разложение по конкретным типам смысла, что диагностически полезнее.

## **Условия (arms) для сравнения**

1. **Только тайлы** — A может отвечать исключительно ID тайлов через пробел/плюс, никакого текста. Это основной тестируемый режим.  
2. **Свободный текст** — тот же набор карточек, но A и B общаются обычным языком. Даёт верхнюю границу для сравнения — без неё непонятно, много ли теряется именно из\-за протокола.  
3. **(опционально) Эмерджентный режим** — A разрешено комбинировать тайлы в порядке, не описанном в примерах `GRAMMAR.md`, чтобы увидеть, начинают ли две модели сами вырабатывать устойчивые конвенции сверх задокументированной грамматики.

## **Метрики**

* **Успешность по слотам** — доля совпавших слотов по всем карточкам (не бинарный успех/провал, а процент).  
* **Длина сообщения** — количество тайлов против количества токенов в текстовом режиме — прямая проверка тезиса о компрессии.  
* **Соответствие грамматике** — использовал ли A только валидные ID и правильный порядок (BASE+QUALIFIER и т.д.).  
* **Кросс-модельная устойчивость** — обязательно прогнать хотя бы одну пару "разные модели" (не только одна модель сама с собой), иначе есть риск, что две копии одной модели угадывают друг друга через общие внутренние представления, а не через сам протокол — это главный конфаунд подобных self-play экспериментов, его нужно явно контролировать.  
* **Разбор ошибок** — какие именно слоты теряются чаще всего (например, отрицание вообще не считывается, а место — считывается всегда) — это сразу диагностика слабых мест грамматики, а не только модели.

## **Лестница сложности**

Раунд 1 — один концепт на карточку (только нужда). Раунд 2 — два\-три концепта (нужда \+ отрицание \+ количество). Раунд 3 — двусторонний диалог: Receiver может задать один уточняющий вопрос тайлами в ответ, прежде чем дать финальный ответ — проверяет не только кодирование, но и способность к переговорам внутри протокола.

## **Как реально прогнать это с текущими инструментами**

Практически это можно организовать как двух отдельных фоновых агентов: одному даю приватный сценарий и бриф с полным лексиконом и грамматикой, второму — только правило "ты видишь исключительно последовательность тайлов, отвечай реконструкцией и предложенным действием". Сам выступаю судьёй между раундами, фиксирую валидность и совпадение слотов, веду лог в файл, в конце считаю метрики по всем раундам и обоим режимам (тайлы vs текст).
