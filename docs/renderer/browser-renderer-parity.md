# Browser Renderer Parity — Technical Spike 01

> Status: technical spike result
> Date: 2026-09-11
> Scope: browser-side Renderer candidate only; no Composer UI, language change, grammar change, vocabulary change, Entity Symbol change, Numeric Notation change, canonical SVG redraw, tag, release, or push implied.

## Question

Can Pictiq support a browser-side Renderer implementation that consumes the same canonical data and produces functionally equivalent output to Python Renderer v0.1 without creating a second drifting interpretation of Pictiq?

## Renderer responsibility map

Python Renderer v0.1 currently combines several responsibilities, but Composer preview does not need all of them inside the browser renderer itself.

| Area | Current Python location | Browser preview need | Spike boundary |
| --- | --- | --- | --- |
| Canonical-data loading | `pictiq_renderer.registry.Registry` | Yes | Use generated browser asset manifest derived from registries and canonical SVG files. |
| Message parsing / schema validation | `pictiq_renderer.parser`, `pictiq_renderer.validator` | Yes, before rendering | Keep outside the rendering core for this spike; browser renderer accepts canonical normalized Message JSON. |
| Legacy normalization | `normalize_and_validate_message` plus `lexicon/compatibility.json` | Yes, before rendering | Shared normalizer/validator boundary; do not duplicate compatibility logic in renderer. |
| Registry/entity resolution | `Registry` | Yes | Manifest contains ordinary icons, Entity Symbols, and numeric assets generated from source data. |
| Numeric notation rendering | `Registry.number_path`, `notation/numeric/index.json` | Yes | Use generated numeric asset lookup; only current implemented number `50` is supported. |
| COLOR parameter handling | `svg_renderer.render_svg` | Yes | Token-local `params.color` is preserved for icon tokens only. |
| Deterministic layout | `pictiq_renderer.layout.layout_message` | Yes | Browser renderer reimplements the small deterministic layout formula. |
| SVG assembly | `pictiq_renderer.svg_renderer` | Yes | Browser renderer assembles nested canonical SVG assets with matching token/frame wrappers. |
| Diagnostics | validator and CLI | Yes, mostly before rendering | Renderer fails clearly for impossible rendering input; rich diagnostics remain validator-owned. |
| CLI-only behavior | `tools/pictiq_render.py` | No | Not included in browser candidate. |

## Source of truth

Python source code is not the semantic source of truth. The source of truth remains the accepted Pictiq architecture and data:

- Message Schema;
- registries;
- compatibility metadata;
- Numeric Notation;
- Entity Symbols;
- canonical SVG assets;
- Renderer behavior/specification.

Python Renderer v0.1 remains the reference implementation. Browser Renderer is a secondary implementation candidate that must conform to the same behavior.

## Browser implementation path

The spike implements a small ES module at [`browser-renderer.mjs`](browser-renderer.mjs). It accepts canonical normalized Pictiq Message JSON and returns SVG.

The candidate deliberately does not implement shorthand parsing, legacy normalization, profile/context warnings, semantic diagnostics, palette behavior, workspace state, export controls, drag/drop, AI translation, persistence, or any Composer UI.

## Canonical-data reuse strategy

Browser assets are generated by [`../../tools/generate_browser_renderer_assets.py`](../../tools/generate_browser_renderer_assets.py) into [`generated/pictiq-browser-assets.mjs`](generated/pictiq-browser-assets.mjs).

The generated manifest is derived from:

- `lexicon/icon-index.json`;
- `entities/entity-index.json`;
- `notation/numeric/index.json`;
- `icons/svg/*.svg`;
- `entities/svg/*.svg`;
- `notation/numeric/svg/*.svg`.

This keeps ordinary IDs, Entity IDs, Numeric Notation assets, and SVG geometry out of hand-maintained browser code. The generated file may be committed as a static Pages artifact, but it must be reproducible.

## SVG asset strategy

The spike chooses a generated browser asset manifest rather than direct per-SVG fetches. This is acceptable for the candidate because it is deterministic, works under static hosting, needs no server, avoids CORS/path ambiguity, and keeps the rendering module simple. The trade-off is bundle size; this is why the verdict includes guardrails.

Future Composer implementation may later split assets or lazy-load by palette/profile/context, but any change must retain parity tests against Python Renderer v0.1.

## Normalization boundary

Preferred boundary:

```text
Composer / import layer
→ shared normalization and validation
→ canonical normalized Message JSON
→ Browser Renderer
→ SVG preview
```

The browser renderer does not own legacy compatibility migration in this spike. The parity corpus includes a legacy shorthand input only after it has been normalized by the Python reference path into preferred current IDs.

## Diagnostics boundary

Renderer diagnostics should stay focused on impossible rendering input, such as a missing canonical asset or unsupported token type. Schema, profile/context, legacy, entity-alias, and parameter diagnostics belong to the normalizer/validator layer before rendering. This keeps the browser renderer from becoming a second semantic interpreter.

## Parity contract

Reference implementation: **Python Renderer v0.1**.

Secondary implementation: **Browser Renderer candidate**.

Parity is structural and functional, with byte identity recorded as a useful signal but not required forever. Required comparison covers:

- same root SVG dimensions and viewport;
- same frame order and token order;
- same token coordinates and tile size;
- same ordinary icon, Entity Symbol, and number resolution;
- same canonical SVG artwork embedded for each token;
- same `currentColor` / token-local COLOR behavior;
- same Numeric Notation rendering for implemented values;
- same normalized legacy result when browser receives normalized canonical JSON;
- same clear failure on impossible rendering input.

SVG serialization details that do not affect structure, layout, token identity, artwork, or color should be normalized before comparison. “Looks roughly the same” is not an acceptable parity level.

## Static GitHub Pages viability

The browser candidate can operate under GitHub Pages/static hosting with:

- no server dependency;
- no Python runtime;
- no external rendering service;
- no API key.

The only required static inputs are the browser renderer module, the generated asset manifest, and canonical normalized Message JSON.

## Alternatives considered

| Architecture | Deployment complexity | Runtime weight | Static/offline fit | Drift risk | Maintenance | Composer fit |
| --- | --- | --- | --- | --- | --- | --- |
| Backend Python Renderer API | Higher | Low in browser | Weak | Low if API is sole renderer | Requires hosting and API lifecycle | Good for controlled apps; poor for pure Pages. |
| Python-in-browser / Pyodide / WASM | Medium to high | High | Possible but heavy | Lower semantic drift | Loader/filesystem complexity | Likely too heavy for v0.1 public Composer. |
| Browser secondary implementation with generated canonical data and parity tests | Low to medium | Moderate manifest size | Strong | Controlled by parity tests | Requires conformance discipline | Best fit for static Composer v0.1. |

## Spike verdict

**ACCEPT_WITH_GUARDRAILS**

The browser secondary renderer is viable for Composer preview if it remains small, consumes generated canonical data, and stays gated by parity tests against Python Renderer v0.1. The guardrail is mandatory: do not leave a browser renderer path in the project without automated parity coverage.
